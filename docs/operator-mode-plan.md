## 0 设计边界与协议依据

### 0.1 三条边界

| 边界 | 内容 | 推论 |
|---|---|---|
| **一条连接 = 一个机器人身份** | 协议原文：`MyMqttClient` 的 `clientID` 需填入**所连接机器人对应的 ID 编号** | 想同时拿 N 台的数据，就要 N 条连接 |
| **全局域 / 单机域二分** | 全局域广播（全队 + 敌方一份），单机域只对绑定的那条连接下发 | 总控模式的底座 = 全局域 + 连接池汇聚的单机域 |
| **图传与 MQTT 无关** | 图传走独立 UDP（3334） | 单兵模式的图传永远是可靠的底层，不受连接数影响 |

### 0.2 数据可得性（连接池建成后）

| 类别 | 内容 | 覆盖范围 |
|---|---|---|
| **全局域**（一条连接即可） | `GameStatus`、`GlobalUnitStatus`、`GlobalLogisticsStatus`、`GlobalSpecialMechanism`、`Event`、`PenaltyInfo`、`RadarInfoToClient` | 全队 + 敌方 |
| 可得字段 | 全队与敌方血量（10 槽位）、己方累计发弹量、全场位置（雷达 12 槽位）、基地/前哨站血量与状态、经济/科技等级/加密等级、堡垒机制计时、事件流、判罚、阶段/倒计时/局数/比分 | 全队 + 敌方 |
| **单机域**（每条连接各自一份） | `RobotStaticStatus`、`RobotDynamicStatus`、`RobotModuleStatus`、`RobotPosition`、`RobotRespawnStatus`、`RobotInjuryStat`、`Buff` | **连接池覆盖的每一台** |
| 由此可得（队友） | 实时热量/上限、剩余弹量、等级、主控模块状态、复活进度、朝向、Buff | **己方全队** |
| 仍不可得 | 敌方单机域字段（协议只下发己方单兵消息） | 敌方只有血量与雷达点位 |

### 0.3 协议依据（逐条核实，来源见附录）

| 结论 | 依据 | 出处 |
|---|---|---|
| 协议**未**禁止或限制多连接 | 全文检索无连接数、并发数、"仅允许一个客户端"类条款 | 协议 §2 全文 |
| Client ID 就是机器人编号 | "`MyMqttClient` 的 `clientID` 需填入所连接机器人对应的 ID 编号" | 协议 §2 通信流程 |
| **单机域结构上只能单播**（决定性证据） | `RobotDynamicStatus` 共 13 个字段，**没有一个字段是机器人编号** → 若同一 topic 上混入多台数据，客户端无法分辨归属 | 协议 §2.2.11 |
| 少数单机域带编号，理论上可广播 | `RobotStaticStatus` 含机器人 ID（第 4 项）；`RobotPosition` 含（第 5 项）；`Buff` 含（第 1 项） | 协议 §2.2.10 / §2.2.13 / §2.2.14 |
| 协议支持按机器人定向寻址 | `MapClickInfo` 有"发送范围（0=指定客户端/1=除哨兵/2=包含哨兵）"+"目标机器人 ID 列表（固定 7 字节）"；"7"即一队机器人规模 | 协议 §2.2.17 |
| 副电脑**不应**做控制端 | 键鼠指令来源"为官方选手端或自定义客户端，**同时仅能通过一个来源**生成发送给机器人的键鼠指令" | 协议 §2.2.1 |

**推论链**：`RobotDynamicStatus` 没有机器人编号字段 → 它只能被单播给"绑定了那台机器人"的连接 → 想同时看全队的实时热量/弹量/等级/主控/复活，**必须**用多条连接各绑定一个编号 → 协议没禁止多连接 → 方案成立。

**唯一仍需实机确认的点**：裁判端是否容许来自同一台电脑的多个自定义客户端同时在线（同一 Client ID 会互相顶掉是确定的；不同 Client ID 在同一台机器上并行，本地演示环境已验证可行，实机待确认）。这是"验证"而非"假设不可行"。

## 1 两个模式的定位

| | 单兵模式 | 总控模式 |
|---|---|---|
| 使用者 | 单个操作手（看自己这台） | 指挥 / 观察位（看全队） |
| 主视觉 | 全屏图传 + 半透明 HUD | 战术地图 + 全队状态列表 |
| 信息底座 | 图传 + 本机单机域 + 全局域 | 全局域 + **连接池汇聚的全队单机域** |
| 核心问题 | "我还能不能打、队友还剩谁、敌人从哪来" | "全队什么状态、谁需要支援、敌方在哪" |
| 与现有代码 | **重构**（单兵视角 → 单兵模式） | **升级 + 扩容**（总控台 → 总控模式） |

两个模式共用同一条主连接与同一份状态模型；连接池只在需要全队数据时扩容，切模式不重连、不换数据源。

## 2 架构地基：RobotLinkPool + 每台机器人快照

### 2.1 选择性订阅（控制增量）

| 链路 | Client ID | 订阅 topic |
|---|---|---|
| **主链路**（本机） | 本机编号 | 协议表 2-1 全部 14 个 topic（`receiver.cpp:8-13`） |
| **队友链路** × N | 各队友编号 | 只需 7 个单兵域：`RobotStaticStatus`、`RobotDynamicStatus`、`RobotModuleStatus`、`RobotPosition`、`RobotRespawnStatus`、`RobotInjuryStat`、`Buff` |

全局域永远只收一份，事件时间线不会被刷屏，带宽增量只有队友的单兵数据。

### 2.2 连接池设计

新建 `src/robot_link_pool.h/.cpp`：

- 每条链路一个 `StatusReceiver`（`receiver.h:16` 的 `start(host, port, robotId)` 已支持指定编号，**协议层无需改动**）。
- Client ID = 目标机器人编号；接收端给每条链路打上编号标签后再进模型：`applyDynamic(linkId, value)`。
- 建连与重连：**串行建连**（每条间隔 200–400ms）；重连加抖动（现有固定 2000ms，`receiver.cpp:20`，N 条同频重连会打爆 broker）。
- 单条链路失败不影响其他链路，独立上报状态。
- 状态上报 `linkChanged(int robotId, bool ready, QString text, int subscribedTopics)`，供链路池面板显示。
- 生命周期建议**常驻**：连接时按当前模式需要的编号集合建池，切模式只增减订阅集合，不拆不建（现场反复重连风险更大）。

### 2.3 MatchState 改造：增量法，把风险压到最低

1. 新增每台机器人快照：

```cpp
struct RobotSnapshot {
    rm::RobotStaticStatus stat;      rm::RobotDynamicStatus dyn;
    rm::RobotModuleStatus mod;       rm::RobotPosition pos;
    rm::RobotRespawnStatus respawn;  rm::RobotInjuryStat injury;
    qint64 statAt = -1, dynAt = -1, modAt = -1, posAt = -1, respawnAt = -1, injuryAt = -1;
};
QHash<int, RobotSnapshot> robots;    // key = 机器人编号（1–9 / 101–109）
```

2. **保留现有 `robotStatic` / `robotDynamic` / `robotModule` / `position` / `respawn` / `injury` 字段作为"本机镜像"**，只在消息来自本机编号时写入。这样 `robot_list.cpp`、`analysis_panel.cpp`、`minimap.cpp`、`respawn_panel.cpp` 这 4 个现有面板**一行都不用改**。
3. `applyXxx` 增加带编号的重载 `applyDynamic(int robotId, const rm::RobotDynamicStatus &)`；旧的单参版本保留并转调本机编号，`tests/core_test.cpp` 现有断言不受影响。
4. 新增访问器：`robot(int id)`、`hasRobot(int id)`、`robotAgeMs(int id, Domain)`、`isRobotStale(int id, Domain)`、`lastLinkIdFor(int id)`（区分"未建链 / 已建链未收到 / 已过期"三态）。
5. 新增**一条**粗粒度信号 `robotsChanged()`，由现有 200ms `ticker`（`window.cpp:500`）兜底刷新。**不要**为 N×M 个域组合加信号（现有 13 域已有 16 个信号，`match_state.h:86-101`，再乘 N 会失控）。
6. `reset()`（`match_state.cpp:49-51`）同时清空 `robots`。

**注意**：即使用户只用单兵模式（1 条连接），第 1、4 步也必须做 —— 因为 `RobotStaticStatus`/`RobotPosition`/`Buff` 带机器人编号，一旦服务器广播，现有实现会把别台数据写进"本机"字段。按编号归集是**无论哪种下发模型都正确**的做法。

## 3 快捷键与交互约定

| 键 / 控件 | 作用 | 生效范围 |
|---|---|---|
| `Ctrl+Tab` | 单兵模式 ⇄ 总控模式 | 全局 |
| `F10` | 进入 / 退出**专注模式**（单兵模式：全屏图传 + HUD 全部保留） | 单兵模式 |
| `Esc` | **退出专注模式**（专注态含全屏，一次退到底）；非专注的纯全屏态则退全屏 | 全局 |
| `F11` | **纯全屏，无 HUD**；与专注态互斥 | 全局 |
| `M` | **开关地图**：单兵模式切右上角 HUD 地图，总控模式切中央战术地图 | 两个模式 |
| 复选框「信息叠加」 | 开关 HUD 整体（关掉只剩纯图传） | 单兵模式 |

**Esc 链必须重写**：现在是"先判全屏、再判专注"（`window.cpp:496-498`）。新语义下专注态本身包含全屏，必须先判专注，否则会出现"退了全屏但仍在专注态"的中间错误状态。

**M 键的实现细节**：底部日志是 `QPlainTextEdit`（`window.cpp:81`），焦点在其中时按 M 会被当作文本输入；`QShortcut` 默认 `WindowShortcut` 上下文仍会抢键，必须显式判断焦点控件，否则操作手一打字就切地图。

**D4 队友面板 + 本机卡**：`TeammatePanel` 按固定槽位 **1/2/3/4/7 出 5 行**（`match_state.h:59-63` 的 `allyHealth(0..4)`），每行：兵种 + 血量 + 血条 + 存活/阵亡 + 位置时效点；本机行高亮。左下本机卡：血量/热量（含上限）、弹量、等级、主控。
**字段自适应**：热量/弹量/等级/主控这几列只在"该台有 per-robot 快照"时才渲染 —— 单兵模式默认 1 条连接时队友列自动不出现（见 D15 与 §9 C3），接上连接池后自动补齐，**不返工**。
验收：5 行全部来自协议槽位；槽位缺失显示"未提供"；`UnitStatus` 过期整面板灰显。

**D5 右上角全场地图 + M 键**：`MinimapPanel` 增加 HUD 模式（半透明深色卡底、去页脚、紧凑点位、`is_high_light` 环保留 `minimap.cpp:139-143`）；底图与坐标**完全复用** `:/map/field.jpg` + `map_transform`，不重新实现坐标。M 键开关显隐（`QSettings` 记住）；总控模式中央地图复用同一控件。
验收：地图常驻可见；M 键即时生效且不与日志输入冲突；过期标注"仅显示最后已知位置"。

**D8 渲染分层**：`VideoStage` 只重绘画面；`OperatorHud` 独立刷新节奏（200ms ticker + 数据域信号，5–10Hz，**不跟帧率**）；HUD 底卡用预渲染 `QPixmap` 缓存；地图复用 `rendered/renderedKey` 缓存（`minimap.cpp:96-107`）。
验收：`decoded_frames` 与改造前同量级；实机 1080p60 单独压测。

### 批次 C —— 连接池地基（P2，总控模式的前提）

**D10 `RobotLinkPool`**：按 §2.2 实现。
**先做最小验证再全量实现**：实机建 2 条链路（本机 + 一个队友编号），确认裁判端接受、官方选手端不受影响、且确实收到那台队友的 `RobotDynamicStatus`。这是本计划唯一"结论可能改方案"的环节，越早验证越好（不阻塞 A/B 批编码）。

**D11 `MatchState` 每台机器人快照**：按 §2.3 增量法实现。重点：旧字段保留为本机镜像，保证 4 个现有面板零改动。

**D12 全局域去重 + 选择性订阅**：按 §2.1 实现；再加兜底去重（状态类按内容哈希，事件类按 `(event_id, param)` 1.5 秒窗口）。
验收：起 7 条链路后事件时间线条目数与单链路一致。

### 批次 D —— 总控模式（P3）

**D13 我方全队列表**：新建 `FleetPanel` 只用于我方，每台一行：兵种/编号 · 血量/上限 · 热量/上限 · 弹量 · 等级 · 主控 · 复活进度 · 位置时效 · **数据来自哪条链路**（区分"未建链 / 已建链未收到 / 已过期"）。敌方继续用 `RobotListPanel`（协议不提供敌方单兵域，只显示血量，不为拿不到的字段留位）。新增全队汇总：存活 n/5、阵亡列表、平均热量、总剩余弹量。

**D14 链路池状态面板**：N 条连接的健康度（Client ID、已订阅 topic 数、最后收到时间、该台是否已有单兵数据、重连次数）。现场排障的唯一入口。

**D15 队友面板补齐 + 图传口径**：连接池可用后，单兵模式 `TeammatePanel` 按 D4 的自适应规则自动补上热量/弹量列。图传口径：`VideoReceiver`（`video.h:15`）是单 socket + 单 ffmpeg 进程，多路需要 N 个 UDP 端口 + N 个解码进程，7×1080p60 不可行 → 总控模式保持**单路主图传预览 + 可切换看哪一台**；多路缩略图列为待确认（§9 C8）。

## 9 风险

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **R1** | 裁判端是否容许同机多个自定义客户端同时在线（不同 Client ID） | 中高 —— 决定总控模式能否拿到全队单机域 | 批次 C 第一步做 2 条链路最小验证；本地环境已验证"不同 Client ID 并存"可行 |
| R2 | 副电脑若使用某台机器人的编号，可能与那台官方选手端互顶（**同** Client ID 才会顶） | 中 | 避开操作手正在使用的编号，或确认裁判端策略；连接前给出提示 |
| R3 | 全局域被推 N 份 → 事件时间线刷屏、带宽放大 | 中 | D12 选择性订阅（队友链路只订 7 个 topic）+ 内容哈希与时间窗兜底去重 |
| R4 | N 条链路同频重连打爆 broker（现有固定 2000ms，`receiver.cpp:20`） | 中 | 重连加抖动、串行建连、单链路失败不扩散 |
| R5 | 某台未上场/未登录 → 该链路连上但收不到单兵消息 | 中 | D11 `lastLinkIdFor(id)` + D13 三态区分 |

| R7 | HUD 半透明控件叠在自绘视频控件上可能闪烁/残影 | 中 | HUD 作为 `VideoStage` 子控件、非不透明自绘，不依赖合成器 |
| R8 | `KeepAspectRatio` 黑边导致 HUD 锚定错位 | 中 | D2 `VideoStage` 固定 16:9，HUD 对齐 `imageRect()` |

## 10 需要你确认的取舍

**C1（最关键）** 连接池的编号范围：总控模式默认订阅己方哪些编号？建议 **1–7**（英雄/工程/3 个步兵/空中/哨兵）；8 号飞镖、9 号雷达是否也要？编号越多，连接数与带宽越高。

**C2 单兵模式默认是否也扩池**：(a) 默认只连本机 1 条，勾选"订阅队友"后才扩（**我的建议**，保守、少占用）(b) 默认就扩全队，队友面板一进去就带热量。

**C3 队友面板字段**：已确认 5 个槽位（1/2/3/4/7）。热量/弹量/等级在连接池可用后自动补齐；是否同意"单兵模式下只在开启全队订阅时显示"？

**C4 M 键作用域**：两个模式各切自己的地图；日志框聚焦时屏蔽。是否同意？

**C5 顶部信息条内容**：默认 = 阶段名 + 倒计时 + 局数 + 机制计时 + 本机身份 + 两枚链路时效。要不要加 (a) 双方基地血量/存活比的局势摘要（不含比分）(b) 最近一条战场事件的短时提示？

**C6 F11 是否保留**：专注态（F10）已含全屏，F11 只作"纯全屏无 HUD"。不需要纯画面模式可删。

**C7 比分**：单兵模式清零、总控模式保留 —— 是否同意？

**C8 图传多路**：总控模式是否需要同时看多台图传？需要的话要先确认官方多路流的端口/流分配（协议与文档均未写），且 7 路 1080p60 解码不可行，得先定降级策略。

**C9 非专注态下侧栏与日志**：我建议保留但收窄（现场需快速重连）。
